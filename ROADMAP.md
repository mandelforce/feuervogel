# Technical roadmap

Goal: make FEUERVOGEL 89 easier to understand, safer to change and possible to port, without changing how it plays or how scores compare.

**Ground rule for every step:** a pure move or rename. Scoring, continues, difficulty and leaderboard rules stay exactly as they are. From Phase 2 on, each step must reproduce identical replay results (score, stage, kills) before it merges. Work on a branch, never push to `main` without OK.

## Where things stand

- `index.html` is about 7,700 lines. About 7,400 of them are one script inside one function.
- No classes, no modules. 484 top-level functions, about 250 top-level variables.
- Game state is global: `score`, `lives`, `stage`, `player`, `enemies`, `ebul`, `state`, `stats` are touched from everywhere.
- Behaviour is chosen by type name: about 98 `.type === '...'` checks and 117 `case '...'` branches.
- Very large functions: `drawProtoPlane` (629 lines), `update` (367), `render` (187).
- 66 lines are longer than 400 characters.
- 161 `Math.random` calls, so runs cannot be replayed.
- 30 `localStorage` calls and 38 empty `catch {}` blocks.
- Version number lives in both `index.html` and `sw.js`, bumped by hand.
- Tests: one smoke test (CI) and a balance bot (manual). No unit tests, no regression test for scoring.
- Sprites, music and fonts are generated by code, not files.

## Phase 1: Cleanups (no gameplay change, low risk)

- [x] Remove the unreachable phone-vibration code (iOS switch hack, `navigator.vibrate`). The `HAPT` table and `haptic()` calls stay: they drive controller rumble. Phone haptics were dropped; don't re-add.
- [x] Delete the stale `old-check.html` (a v1.1.1 copy, ignored by git).
- [ ] Export the live Cloudflare Worker into `worker.js` (it has `/status` and the best-score table the repo copy lacks), so the repo is the real source. Add blocks, never replace wholesale.
- [x] Add a `store` wrapper (and a `KEY` list) for all `localStorage` access. Every key name is unchanged.
- [x] Fill in the "Project structure" section of `CLAUDE.md` (a local file, not in git) and add `ARCHITECTURE.md`.
- [x] Unit tests for the Worker rules and ISO week labels (`tests/worker.test.mjs`, run in CI). Still open: game-side helpers (collision, score extends); they become testable once the code is in modules (Phase 3).

## Phase 2: Safety net

- [x] Replay test: three bot scenarios with a seeded `Math.random`, compared with `tests/golden.json` (`tests/replay.mjs`). Works from outside the game, so the game code is untouched. In CI as an advisory step until proven stable.
- [ ] One seeded RNG inside the game for everything that affects gameplay. Cosmetic effects (clouds, sparks) may keep `Math.random`. Until then the replay test needs a fresh page per scenario and a stopped frame loop.
- [ ] Terrain is generated under a per-frame time budget (`ensureChunks`), so what exists at a given frame depends on machine speed, and spawns read the terrain. Make generation deterministic (by frame or position, not by clock). Needed before any server-side replay check.
- [ ] Ambient state (weather timers, birds, clouds) draws random numbers and keeps running while the title screen idles, so a run's randomness depends on idle time. Reset or isolate it when a run starts.
- [ ] Run the replay test as a required CI check once it has proven stable.
- [ ] Optional later: store a replay with submitted scores to allow server-side checks. Needs a decision first, as it touches leaderboard rules.

## Phase 3: Modules

Use plain ES modules, no bundler. GitHub Pages serves them as they are.

```
src/
  sprites/      pixel art and palettes
  audio/        music, FM/OPL synths, sfx table
  world/        terrain, chunks, themes
  entities/     enemies, bosses, bullets, pickups
  ui/           title, menus, results, HUD
  leaderboard.js
  storage.js
  input.js
  main.js
```

- [ ] Move the pure, dependency-light parts first: sprites, music, fonts.
- [ ] Then the leaderboard client and storage.
- [ ] Update `sw.js` so every module is in the offline cache. The smoke test already checks listed files exist.
- [ ] One place for the version number (`VERSION` read by the service worker, or a tiny build step).
- [ ] Run Prettier once, as its own commit with no other changes, so `git blame` stays useful.

## Phase 4: Structure

- [ ] **Entity table.** Each enemy type declares its stats and its own `update`, `draw` and `onKill`. `update()` and `render()` loop over entities. Start with bosses (`BOSSDEF` and `BOSSMOVE` are already close), then ground enemies, then air.
- [ ] **One `Game` state object** instead of scattered globals. `newGame()` becomes `createState()`. All score changes go through one function, so scoring has a single home.
- [ ] **Input layer.** Keyboard, mouse, touch and gamepad produce one intent object (`move`, `bomb`, `pause`).
- [ ] Break up `update`, `render` and `drawProtoPlane` into named steps.

## Phase 5: Port-ready

- [ ] Simulation (`update`) has no canvas or DOM calls. Rendering reads state only.
- [ ] Render calls go through a small interface so another backend (WebGL, native) can replace the canvas one.
- [ ] Script to export generated sprites and audio to files, for an engine port.
- [ ] Try a web wrapper (Capacitor or Tauri) first; it should need little change.

## Open decisions

- Should replays be sent with scores? (leaderboard rules, ask first)
- Add a build step (esbuild or Vite), or stay with plain modules?
- Does Generative mode get its own board? (already undecided, see `CLAUDE.md`)

## Suggested model use

Phases 1 to 3 are mostly mechanical and fine at the default setup. Use the strongest model for Phase 4, where changes reach scoring paths across the whole file.
